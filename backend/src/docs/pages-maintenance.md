# Pages automatic updates and Pages upkeep

The interactive Assistant uses the selected runtime's native tools, configured MCP servers and ordinary permission settings, except Approve for me: on Kiro V3 the Assistant keeps Kiro's default policy. Its Michi tools retain workspace ownership and protected-page edit rules. Background maintenance can modify Michi state and use external read-only MCP tools through its checked tool gateway. These background restrictions do not apply to interactive Assistant chat.

Applies to: native Pages and Pages upkeep, the agent's local background maintenance (earlier versions called it the Meta agent), in this backend source. Source checked: 2026-11-12. Runtime support below is a source contract, not live provider or installed-app acceptance. See `pages-and-components` for editing and `page-component-design` for component styling.

## Kinds of work

| Path | What it reads | What it changes |
| --- | --- | --- |
| Pages Assistant | Accessible Michi work requested in the conversation, using Michi integration tools plus the selected runtime tools | Requested pages/rows; protected content becomes a suggestion; new ordinary conversations require the start-conversation approval flow |
| Initial workspace-home generation | Eligible conversations in that workspace within the configured initial look-back | Only its assigned workspace home, citing messages actually read |
| Automatic conversation maintenance | Newly completed, readable conversation turns in an enrolled workspace | Eligible pages/databases through verified write/proposal receipts, or explicit no-change decisions |
| Watch check (see **Workspace instructions and watches**) | Outside sources through read-only tools, on the watch's interval, and the workspace's eligible pages/databases | The same eligible resources, with one final write or no-change decision per resource per check |
| Check-in (your agent's own look when something needs you, a conversation it started finished, or the morning brief, **Settings → Michi → Updates**; not part of Pages upkeep) | What changed in the sources it watches, through Michi's read tools and its own | Pages and databases of unarchived workspaces whose AI navigation is on, never the Pages Home: per check-in at most 5 write calls, 40 changed blocks, rows, columns or views, 1 new page and 1 new database, and 20 write calls a day. Nothing that loads from outside Michi; links only to Michi, in-page anchors and the work sites it watches. Protected content becomes a suggestion. Its post in the Assistant's conversation lists what it changed, with **Undo all** (also in **Activity…** in the panel's ⋯ menu); see **Content a check-in wrote** in `pages-and-components` |

Pages Home also has a separate summary pass. It reads workspace home pages, not their original conversations, and writes only its assigned Home. It removes conversation-source claims from those summary writes rather than pretending it read the underlying messages. Progress cards are separate from a durable task database: a completed reply/run does not by itself mean a business task is done.

## Runtime and scope

Initial generation and maintenance run on **Settings → Michi → Model → Background work** (the Settings page is named after your agent: Michi unless you renamed it), which check-ins use too: **Same as conversations** follows **Settings → Runtime & model**, **Custom** sets a runtime, model and reasoning of their own. What Pages upkeep keeps up to date, and how far back it first reads a workspace (**First read**), is under **Settings → Michi → Pages**. The Pages Assistant runs on the global runtime and model from **Settings → Runtime & model**, not on Background work; when that runtime cannot host the Assistant (Crew, Antigravity), it uses the first available of Claude, Codex, Pi and Kiro. A runtime, model or reasoning picked in an Assistant conversation's composer stays with that conversation. Pi, Claude, Codex and Kiro support these paths. **Kiro Crew and Antigravity are not supported for background work**; that does not remove their ordinary chat capability. Initial generation and background maintenance must pass their adapter's actual tool-catalog check; an unsupported or unexpectedly broad catalog fails with a restriction error. Interactive Assistant chat does not use that closed-catalog check.

The maintenance profile grants Michi state operations and external read-only access through maintenance_list_tools and maintenance_call_tool. The gateway discovers external tools from the local MCP configuration used by Pi discovery, independently of the selected AI runtime; it does not import CLI-private MCP configurations. External tools need readOnlyHint=true and must not declare destructiveHint=true; any other tool is neither listed nor run, and a call to it answers `unavailable` with the read-only alternatives, after fresh discovery. Nobody approves tools for background work: there is no approval to give. The agent must try permitted alternatives and must not mark blocked work complete. Internal tools retain their ownership, validation and active-run checks. Starting or messaging unrestricted workers is not a Michi-only effect and is not exposed. It does not become a general coding session when the ordinary chat permission mode is Trust/YOLO. Maintenance cannot run arbitrary shell/code or write outside Michi. It can create and modify Pages, databases and component-library content through Michi tools. Batch source decisions still use the maintenance writers so receipts and completion accounting remain correct. The Assistant keeps its Michi integration catalog, including documentation and native Page/component tools, alongside ordinary runtime tools and configured MCP servers. Tool availability for an ordinary chat or Agent Run does not imply availability in maintenance.

Pages upkeep reads only this computer's backend. Remote workspaces are not queued or read by it, and their homes show as unavailable; a remote page's **Conversation maintenance** panel works with that machine's own Pages upkeep. Processing requires the backend, scheduler, selected runtime and provider to be available. Closing the Page or the Assistant panel does not stop backend maintenance; stopping its backend does. On macOS, the installed desktop app can keep its backend running after you quit it, as a per-user launchd LaunchAgent that also starts at login: turn on **Settings → Notifications → When Michi’s windows are closed → Keep Michi running after you quit** (**Settings → Scheduled jobs** links to it), or use **Run in background** on the Scheduled page when it is offered; see **Keep the backend running on macOS** in `configuration`.

## Background coordination

Pages upkeep runs only while Michi does: it is off until you turn it on with Get started's **Start** or the switch at the top of **Settings → Michi**, and until then opening Pages queues no first-time generation. One backend coordinator checks for pending maintenance every 60 seconds, and can be woken by an explicit check or completed execution. Checks query local state and do not create an AI session or an empty run record. Only pending history generation, a due watch, conversation work, catch-up/reconsideration, recovery, or a changed Home summary starts a Pages maintenance execution. Automatic memory extraction is a separate execution on the same coordinator and shares its lease, capacity and backoff, but no pause: neither turning Michi off nor a workspace's maintenance pause stops it; only **Settings → Memory → Learn from conversations** does, off until you turn it on. No new conversation does not necessarily mean no pending work.

On the coordinator's own schedule, new conversation work waits until the user has been idle for 10 minutes, 8 completed turns wait, or the oldest has waited 2 hours, the triggers memory consolidation uses; two such batches of an owner start at least 30 minutes apart, across workspaces, unless a full batch (20 turns) waits. A changed Home summary runs at most once an hour after the last successful one, once no workspace home was written for 10 minutes (if homes keep being written, 3 hours after the last attempt), and rereads only the workspace homes that changed since that summary; when a home was archived, deleted or hidden, it rereads every home. A summary runs at once when it takes in a first-time generation (the first run's wrap-up, a retried or new workspace) or a home changed after a **Run now** or **Update** started, until the next summary attempt; a failed one is retried on its own backoff. First-time generation, due watches, catch-up/reconsideration, plans in progress, **Run now** and Retry never wait; a Run now that finds no free run slot starts as soon as one frees up.

Maintenance appears once in Scheduled. It is not a recurring prompt job: ordinary scheduled jobs keep their existing execution semantics. For migration and recovery, maintenance retains internal execution identities in the shared execution ledger, with their old IDs, plans, cursors, receipts and fenced claims intact. These records have no next scheduled time, do not consume the ordinary job quota, and cannot be edited or deleted through the ordinary job API.

Maintenance shares the host execution lease and overall capacity with scheduled jobs. At most one maintenance execution runs at a time, with least recently served workspaces selected first. Failed executions back off; the existing repeated-failure stop and tool restriction checks still apply. Turning Michi off (its switch in **Settings → Michi**, until you turn it on again; it also stops check-ins) prevents new automatic executions and lets current work finish; **Run now** and Retry still run. It preserves each workspace's separate pause and progress. Turning it on does not unpause locally paused workspaces.

The UI distinguishes the last database check from actual update runs. Historical empty checks remain readable; new empty checks only update the coordinator's timestamp and daily counter.

## Enable, pause and catch up

Use a page's **Conversation maintenance** panel. Maintenance is enabled for a workspace and considers all its undeleted page trees except those explicitly excluded. New-page creation offers **Keep up to date from this workspace’s conversations**, which controls the new tree's exclusion. Check existing trees' exclusion settings when enabling workspace maintenance; the current checkbox helper text about existing pages is not an enrollment allowlist. The panel links to **Change in Settings › Michi › Background work** (your agent's name in place of Michi), rather than owning a separate runtime profile. It shows status with **Enable updates** / **Pause** and **Run now** controls. It runs when conversations go quiet rather than on a schedule, so the Scheduled page does not list it; the Pages Home shows one status line only while it is paused, failing or on its first read.

Enabling incremental maintenance starts at the current completion position. It does not silently scan all historical conversations. The explicit initial-home read and its configured look-back are a separate path. Native maintenance pause, disable and re-enable preserve its saved cursor. Generic `conversationUpdates` consumers have separate cursor-reset rules when toggled; do not apply those rules to the native managed configuration.

Page-tree exclusion records the completion interval it missed. Re-enabling makes the page eligible for new work but does not revisit earlier inputs. Use **Queue this period** for an offered, bounded catch-up of a recorded exclusion period; it is limited to that root page and the pages currently under it. **Reconsider** requests another decision for an unfinished/disputed source. It is not permission to repeat arbitrary external actions.

| Status | Meaning |
| --- | --- |
| Not enabled / Paused | Automatic processing is not active; inspect configuration before expecting new results |
| Updating / new turns waiting | Work is running or queued; processing is eventual, not tied to a fixed UI latency |
| Needs attention | A source/resource decision remains unresolved; inspect it and use Reconsider where appropriate |
| Last update failed / Status unavailable | Inspect the recorded error or restore connectivity; a missing status is not proof of completion |
| Up to date | Available inputs have durable decisions; suggestions can still await review, and model relevance judgments can be wrong |

Saving **Layout preferences** alone does not enqueue a model turn or rearrange content. Each maintenance/initial-generation read uses the target page's own preferences and rules; global Home preferences do not propagate to workspace or child pages. A page's preferences take precedence over the default block choices in the initial-generation, Home summary and maintenance prompts; only program-applied section limits override them.

Initial generation has no fixed block set or template. It opens a workspace home with a short callout (at most two sentences): how far the work got, or, where the conversations are thinking rather than building, what the person is still torn about. It then picks two to five blocks by the shape of what it read, such as an open conflict or comparison, a diagram of how concepts relate, a before/after for an overturned view, a grid or tabs for themes developing side by side, a toggle for long reasoning, or, for work that is moving, next steps with owners, checks with states, milestones or reference facts. A thinking page centres on the person's own thinking, not a digest of the assistant's answers: a view or change of mind counts as the person's only when they said it, and the assistant's proposals stay marked as proposals, with whether the person answered. Next steps hold only steps someone decided to take, and every such step; when one has a deadline or holds up other work, next steps come right after the callout. It titles each block in the page's language, and adds metrics only for numbers the work itself produced, never counts of conversations or messages. Later maintenance keeps blocks in shape instead of only appending to them, and lets the page's structure follow the conversations: a lone new idea lands small, a list that grew long or split into themes is restructured, a settled question replaces its open conflict or comparison with what was decided, and a challenged claim becomes an open conflict or a recorded change of view. When a block's content no longer fits its type, maintenance replaces the block with one of a fitting type. On other pages it replaces only blocks no person edited, and a block a person edited is updated in place as a suggestion. On a workspace home or the Pages Home, a block an agent wrote stays the agent's after a person edits or ticks it: the change applies directly, keeping the person's wording and leaving out checklist items already ticked done. Only a block the person added becomes a suggestion. An initial generation that already succeeded does not run again, so new preferences apply through later maintenance.

## Evidence, ownership and progress

Only eligible successful completed conversation turns enter the completion feed. Failed/cancelled/interrupted turns and scheduled inputs do not become new ordinary conversation inputs. Existing history is not backfilled just because this feature is enabled. Edits, restores and imports do not impersonate fresh completions.

The reader uses a bounded completion interval and retrieves original source messages. Empty checks do not invoke a model. Unreadable or oversized inputs remain unresolved instead of being counted as processed. A durable processing plan records eligible resources and routing decisions. Every routed resource needs a verified applied/proposed receipt or explicit no-change decision before its source is considered complete. Routing is final: a routed source can never gain resources. When a run is recovered after routing, `maintenance_list_resources` returns the routed resources with each one's decision and changes nothing. Reading a routed resource again from its first page (offset 0, no cursor) refreshes its revision to the current one; a continuation read cannot. The agent therefore reads again and then writes or records no change from what it read, which also recovers a write refused because its target changed. Writes keep their per-row and per-block revision checks, and a decision that is already recorded is never repeated. A routed resource that was deleted or excluded, or whose page route changed, is skipped with a reason when it is read, so the plan can still finish; the workspace task database instead adopts the new board route, since its tasks belong to the workspace.

A conversation that is editing a page outranks maintenance. While a chat turn holds the page's edit lease (see the **Edit leases** paragraph under **Page tools and write receipts** in `pages-and-components`), maintenance does not read, write or record no change for it: the call fails with `PAGE_BUSY`, the resource stays pending and the run records the deferral. A run that stops with only such pages left succeeds with "Waiting for a conversation to finish editing …; progress retained" and does not advance the cursor or count as a failure. The coordinator starts no run for that plan until the leases end, then resumes it from the recorded progress.

The native writer commits an operation set and its receipt together. Retry identity includes the job, source turn, resource and processing generation. An identical committed payload reuses its receipt; a different payload for that key conflicts. Stale revisions, lost authority or incomplete resource decisions retain progress for inspection. A successful chat response or a prose claim of “done” cannot advance the cursor by itself.

Human-edited fields/blocks retain protection, except a block an agent wrote on a workspace home or the Pages Home: a change to it applies directly, keeping the person's wording and leaving out ticked checklist items. Unlike atomic `edit_page` groups from chat, the maintenance/Home planner may persist permitted edits and protected proposals in the same transaction when all operations plan successfully. A stored proposal is a completed processing decision, not a user acceptance or an applied content change. Do not transfer the chat tool's mixed-group rejection rule to this separate writer.

New Markdown `segmentSources` must use verified evidence. Initial workspace generation may cite only assistant messages returned by its reads. Incremental maintenance may add its acknowledged source and retain existing page evidence. The writer validates message identity and workspace/owner scope before saving. Whole-block change provenance and per-item evidence serve different purposes and are not interchangeable.

## The task database

A workspace's task database (see **Tasks** in `pages-and-components`) is always among the resources maintenance considers for a new completed turn: whether or not a page shows its board, and even when the page tree that shows it is excluded. **Queue this period** does not read it again, because ordinary maintenance already handled those turns.

Once the task database is routed for a source, maintenance finds tasks with `maintenance_list_tasks`: by `nodeId` (the tasks that link that conversation), by words in a task, its next step or its notes (`query`), and by `statuses`. It returns at most 20 compact tasks, newest change first, with their row id and `rev`, who set the status (`statusSetBy`), the conversations waiting on the user now, and `goneConversationIds`: linked conversations deleted or moved to another workspace (a branch archived from the Map is not gone). `more` says there are others; narrow the search. Maintenance writes tasks with `maintenance_write_database`, following the Tasks rules of `pages-and-components`:

- Update the tasks that link the turn's conversation, link the conversation to a task it works on, and add a task only for a goal no task covers; never add one task per conversation.
- A finished turn does not make a task done. Mark a task Done only with evidence that its goal is reached.
- A cell the user edited is theirs, including a status set by dragging a card: a write to it becomes a suggestion the user accepts or dismisses.
- Unlink the `goneConversationIds` of a task you update.
- Do not route the task database for a turn that works on no goal.

On the workspace's board the cards an update added or changed read **New** or **Updated**, its suggestions wait on their cards, and a line above the board says what it did, with Undo while any of it was written. Undo puts back the whole update, including a suggestion from it the person already accepted. All tasks shows none of these marks.

## Workspace instructions and watches

The **Conversation maintenance** panel of an enabled workspace also holds two per-workspace settings. Neither changes the runtime, which stays in **Settings → Michi → Model → Background work**, and editing either does not stop a run in progress.

**Instructions for this workspace** is up to 4,000 characters of text Pages upkeep follows in every run that writes this workspace: conversation maintenance, its first-time generation and each watch. The Pages Home summary spans all workspaces and does not receive them. They never widen the maintenance tools or relax their rules. A page's own **Layout preferences** still govern that page's organization. The workspace's Instructions for its conversations (on its Manage page) are not given to Pages upkeep, on any runtime.

A **watch** is a timed check of outside sources such as tickets or tasks: a name, what to check and where to record it, and an interval from 15 minutes to 7 days. A workspace has at most 10. The workspace's single maintenance execution runs a due watch as its own run, ahead of conversation work. The interval counts from when a check starts, so a failed check is retried at the next interval, not in a loop. **Check now** makes a watch due at once; it runs when the workspace's maintenance is free. Watches run only while workspace maintenance is enabled and not paused, and turning Michi off stops them too. New watches can no longer be added; ask your agent for a scheduled job instead. Existing ones keep running and can still be changed, checked now or deleted.

A check reads outside sources through the same gateway as other maintenance: only read-only external MCP tools run, and any other tool is not run. A check has no source conversation and does not route: `maintenance_read_source` returns the watch and the previous successful check's report (the end of its reply), and `maintenance_list_resources` lists every eligible page and database of the workspace, with excluded page trees and the saved Home Page left out as usual. The check must read a resource from its first range before writing it. It makes at most one final write or no-change decision per resource, against the revision it read, and an exact retry replays that decision. Human-edited blocks and cells become suggestions, as in other maintenance writes, except agent-written blocks on a home page, which update directly. A page a conversation is editing is recorded as waiting and read again by the next check.

A check succeeds only when its tools recorded at least one decision; a reply that recorded none fails the run, whatever it says. Its writes stay whatever the turn did. Each check's result appears on the watch and in the maintenance execution's run history. After 3 failed checks in a row a watch turns itself off and shows why; turning it back on clears that. Cancelled or interrupted checks do not count toward that limit. A check that fails still counts as a failed run of the workspace's maintenance execution.

## Diagnose an update that seems missing

1. Check that the workspace is local, workspace maintenance is enabled, the page tree is not excluded and the backend/scheduler is running.
2. Inspect the Background work runtime/model (Settings → Michi → Model) and any restriction or provider error; changing ordinary chat permissions does not fix an unavailable profile.
3. Check whether the source was a new eligible completed turn, part of an explicit initial read, or requires a catch-up period. New turns can wait for the schedule in **Background coordination**; **Run now** reads them at once.
4. Check page exclusion, **Ignore** protection, pending suggestions, unresolved sources and automatic maintenance history.
5. Read the saved page/receipt and exact Sources before claiming the content changed. A pending proposal or consumed no-change decision may explain the visible result.

## Storage and backup

Pages, database rows, source/change history, layout-preference revisions, processing plans and cursor state are stored in the backend's SQLite database. Conversation Markdown exports and portable JSON backups do not include the complete native Pages state. Preserve the stopped backend's data directory for a complete backup; see `data-and-backups`.

Generic scheduled jobs with `conversationUpdates: true` are a separate consumer: their explicit no-change confirmations do not grant the native maintenance writer's ability to acknowledge Page writes. Both use the scheduler, but their completion rules differ.
